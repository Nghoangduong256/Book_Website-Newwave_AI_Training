# Creating a migration

## The rule that shapes every migration here

> **Add first, backfill second, constrain third, drop in a later release.**

A migration runs while the previous version of the application is still serving. Anything that
blocks, rewrites a large table, or removes something the running code still reads is an outage.

## Steps

### 1 · Write the model, then autogenerate
Autogenerate, then **read and correct the output before committing it.** Never commit it unread:
generators miss server defaults, get enum changes wrong, and reorder operations in ways that fail on
a populated database.

### 2 · Check the common columns
Every business table: `id uuid` default `uuidv7()`, `created_at`, `updated_at`, `created_by`,
`updated_by`, `version`, `deleted_at`. Append-only tables may omit the mutation columns **and must
say so in a comment**.

### 3 · Types
Money `numeric(18,2)` + `currency char(3)` — never a float, never a bare amount. Effort
`numeric(8,2)`. Timestamps `timestamptz`. JSONB only for genuinely schemaless payloads.

### 4 · Keys and indexes
Every FK indexed, with an explicit `ON DELETE` (`RESTRICT` by default; `CASCADE` only for genuinely
owned children). Every index justified by a named query.

### 5 · Enums
Adding a value is **two edits**: `ALTER TYPE … ADD VALUE` *and* the application enum class. Doing
only the first raises at runtime, not at migration time. Note that `ADD VALUE` cannot run inside a
transaction block on older servers.

### 6 · Never import application constants
**A constant a migration imports is frozen the day that migration ships.** Next year the enum gains a
value and the migration does something different from what it did on the database it already wrote.
Inline the literal values.

### 7 · Constraints carry business rules
A rule expressible as a `CHECK` belongs in the database: it cannot be bypassed by a new code path.
Name it `ck_{table}_{rule}` so a failure names the rule.

### 8 · Backfill as its own step
A backfill over a large table is batched, resumable, and does not hold a long transaction. If it can
be a background job, it should be.

### 9 · Seeds are idempotent
Running a seed twice produces no duplicates, and there is a test proving it.

### 10 · Verify both directions
- Forward on an **empty** database.
- Forward on a database holding **representative data**.
- Down, or an explicit, loud refusal by design.
- **Then prove metadata and database agree:** a second autogenerate should produce an empty diff.
  That empty diff is the proof; "it ran without error" is not.

## Checklist

- [ ] Autogenerated output read and corrected
- [ ] Common columns present; append-only stated in a comment
- [ ] Money, effort and timestamp types correct
- [ ] Every FK indexed with explicit `ON DELETE`
- [ ] Enum changes made in both places
- [ ] No application constant imported
- [ ] Add → backfill → constrain ordering respected
- [ ] Seed idempotent, with a test
- [ ] Forward on empty **and** populated; empty autogenerate diff afterwards
- [ ] No already-applied migration edited
